# 逆向排查思路：从一台闭源设备到可编程接口

> 这篇不是"我做了什么"，而是"**遇到一台完全不懂的设备时，按什么顺序把它摸清**"。
> 换一个品牌、换一个品类，方法一样适用。

---

## 第 0 步：先想清楚要什么

动手前先定义终点。这个项目的终点不是"破解协议"，而是三条可验证的目标：

1. 设备在**没有厂商服务器**的情况下能正常工作
2. 能从**局域网**读到完整状态（温湿度、水位、风量、模式）
3. 能**可靠地写入**指令（开关、目标湿度、风量）

目标定得越具体，后面越不容易跑偏。反之，如果一开始想的是"把协议全解出来"，
很容易花两周时间在无关字段上。

---

## 第 1 步：画出链路，找到边界

任何联网设备都能抽象成三段：

```
App  ←──────→  厂商云  ←──────→  设备
       ①            ②          ③
```

关键问题：**哪一段是加密的、哪一段是明文、哪一段可以被替换。**

- ①② 之间通常是 HTTPS + 账号体系，破解成本高，且依赖厂商服务器（已停运，此路不通）
- **②③ 之间是设备与云的通信**——这一段才是机会所在

判断方法：抓设备自己的流量，而不是 App 的流量。

**这一步的产出应该是一张图**，不是一堆抓包文件。

---

## 第 2 步：抓设备，不抓 App

### 怎么抓

设备通常连在 2.4G WiFi 上，最省事的方式是让设备连到一个能镜像流量的热点，
或用路由器的端口镜像功能。

### 抓什么

看设备启动后的前 60 秒。这个窗口里设备会完成：DNS 解析 → 建立连接 → 注册 → 心跳。

### 第一个关键判断：协议是什么

本项目最终落在 **MQTT**（1883 端口），而不是 HTTP。这个判断决定了后面所有工作：

| 特征 | 结论 |
|---|---|
| 长连接、心跳包、主题订阅 | MQTT |
| 短连接、请求-响应、Header 里有 JSON | HTTP |
| 二进制帧、固定头长度 | 私有 TCP 协议 |

**为什么这一步重要**：协议不同，可复用的现成组件完全不同。选 MQTT，意味着
可以用 mosquitto 直接搭服务端，不用自己写 socket 层。

---

## 第 3 步：DNS 劫持——把设备骗回本地

### 原理

设备连的是域名（如 `i.airmx.cn`），不是 IP。只要让这个域名解析到你自己的机器，
设备就会把本地服务当成官方服务器。

**这是整个方案的地基。** 不做这一步，后面所有工作都无从验证。

### 怎么做

在路由器的 DNS 转发里加两条记录，指向本机 IP。

### 怎么验证

```bash
dig +short i.airmx.cn @<路由器IP>
```

返回本机 IP 才算成功。

### 失败的样子

设备 Wi-Fi 灯**快闪**——它在反复重试连接。这个现象非常重要，后面排查主要靠它区分
"DNS 没生效"和"服务端有问题"。

### 一个容易忽略的点

改了 DNS 之后，设备可能因为缓存仍然连旧的解析结果。**断电重启设备**，不要只重启服务。

---

## 第 4 步：复现注册流程

设备连上来之后第一件事是注册：告诉服务器"我是谁"，换回一个标识。

### 要观察什么

1. 设备上报了什么（MAC？序列号？型号？）
2. 服务端回了什么（ID？密钥？主题名？）
3. 这个 ID 是**服务端分配**的还是**从 MAC 推导**的

本项目实测：device_id 由 MAC 推导，且每台设备不同。这个结论很重要——
意味着你可以自己算出它，不需要厂商数据库。

### 卡住的典型表现

如果注册一直重试，通常是**回包格式不对**。抓一次真实回包，逐字段比对，
不要自己发明格式。

---

## 第 5 步：指令签名——先搞清楚"哪些字段被覆盖"

设备会校验指令完整性。你不需要立刻搞懂算法，先搞清范围：

### 方法：差分

1. 抓一条**合法**指令
2. 只改一个字段（比如 `cadr` 从 30 改成 31）
3. 观察签名字段是否变化

- 变化 → 该字段参与了签名
- 不变 → 该字段不在签名范围内（通常只有时间戳和指令体参与）

再改时间戳、改指令 ID，逐一定位。

### 判断"指令被接受"的唯一标准

**不是 HTTP 200，也不是回执里的 ok。** 是**读回状态确认设备真的变了**。

本项目踩过的坑：网关返回 `{"ok": true}`，但设备侧静默丢弃了指令。
只信读回值。

---

## 第 6 步：字段探测，建立能力矩阵

拿到可用的指令通道后，开始系统性探测。

### 铁律：一次只改一个字段

同时改两个字段，出问题时无法归因。

### 四类结果，四种结论

| 写入后读回 | 结论 | 处理 |
|---|---|---|
| 等于写入值 | 可写字段 | 可以暴露给上层 |
| 旧值不变 | 只读 / 不支持 | 不暴露 |
| 恒为 1（写 0 仍回 1） | **能力标志**，不是开关 | 不暴露，只在文档说明 |
| 被量化（45→44） | 有步进 | 映射层按步进量化 |

最后一条尤其重要：设备把 `cadr` 量化到偶数。如果映射层不做同样的量化，
用户在界面上拖到 45%，设备回 44%，滑块就会跳。

### 不要照抄 APK

APK 里的字段列表只能当作"可能的字段"，不能当作"支持的字段"。
实测中 `delayOffTimer` / `electrolysis` / `uv` 这类字段在真机上写入全部无效。

**照抄的结果就是做出一堆按了没反应的假开关**——这比少做几个功能更伤。

---

## 第 7 步：从"能控制"到"好用"

协议通了只是开始。真正的难点在语义映射：

| 设备语义 | HomeKit 有对应吗 | 处理 |
|---|---|---|
| 开关机 | ✅ Active | 直接映射 |
| 目标湿度 | ✅ Threshold | 直接映射 |
| 风量 | ⚠️ RotationSpeed 存在但 iOS 不渲染 | 单独挂 Fanv2 |
| 水位 | ❌ 无服务类型 | 放弃，改做 Web 看板 |
| 睡眠模式 | ❌ 无对应档位 | 拆成独立开关 |
| 童锁 | ⚠️ 有特征，无控件 | 保留特征，不做界面 |

**判断标准**：如果一个功能在 HomeKit 里只能做成"按了没反应的开关"，那就不做。
宁可少给，也不要给假控件。

---

## 踩坑清单（每条都是真实踩过的）

| 现象 | 误判 | 真相 |
|---|---|---|
| 设备 Wi-Fi 灯快闪 | 设备坏了 | DNS 指回公网了 |
| 配对后全部"无响应" | 配对失效 | 在 `async_start()` 之前调了 `config_changed()`，覆盖了状态文件 |
| 改了服务顺序，配件全挂 | iOS bug | 服务顺序 = IID，IID 变了 iOS 映射失效 |
| 开关名显示"开关 2" | 名字没传对 | 服务端名字是对的，iOS 没刷新 |
| 自动档调目标，风扇不动 | 代码没下发 | 设备固件不重算，必须真的 0→1 切换 |
| 写指令返回 ok 但没生效 | 代码问题 | 设备静默丢弃，只能读回确认 |
| 同一指令连发两次，第二次无效 | 代码问题 | bridge 有 10 秒节流 |

---

## 方法论总结

1. **先定义终点**，不要以"全解协议"为目标
2. **抓设备不抓 App**，边界在设备与云之间
3. **DNS 劫持是地基**，不做这步无法验证任何东西
4. **回执不可信**，只信读回状态
5. **一次改一个字段**，否则无法归因
6. **不照抄 APK**，实测为准
7. **做不出真控件就不做**，假开关比没有更糟
