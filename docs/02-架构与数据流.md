# 架构与数据流

## 四层拓扑

```
┌─────────┐   MQTT/1883   ┌──────────┐   HTTP   ┌────────┐   HTTP    ┌─────────┐  HAP   ┌────────┐
│ 加湿器  │ ────────────> │  gateway │ <──────> │ bridge │ <───────> │   hap   │ ─────> │ 家庭App │
└─────────┘               └──────────┘          └────────┘           └─────────┘        └────────┘
   设备侧                     协议层              状态层              语义层
```

**为什么拆四层，而不是一个进程干完？**

| 层 | 职责 | 单独成层的理由 |
|---|---|---|
| gateway | 复现设备协议：注册、心跳、指令签名 | 这层绑定设备型号，换品牌要重写 |
| bridge | 状态缓存、指令节流、密钥管理 | 承上启下，HomeKit 层不该关心 MQTT |
| hap | 语义映射：设备字段 → HAP 特征 | 这层可复用到任何设备 |
| — | 家庭 App | 只认标准 HAP |

关键收益：**改 UI 不用碰协议，换设备不用碰 HomeKit**。本项目验证期一天内改了十几次映射，
如果三层耦合，每次都要动协议代码。

## 数据流：一次写入

以「用户在家庭 App 拖动目标湿度」为例：

```
1. iOS  → HAP 写请求（TargetHumidity = 70）
2. hap  → setter 被调用
         ├─ 记录入站（recent_calls）
         ├─ 乐观更新界面（立刻显示 70，不等设备）
         └─ 攒到 1.2 秒再发（防抖，拖动会连发几十次）
3. hap  → POST /devices/{id}/settings {"hThreshold":70}
4. bridge → 合并进 MQTT 指令包，签名后发布
5. 设备  → 执行，回一条状态
6. bridge → 缓存状态，等 hap 来读
7. hap   → 每 8 秒拉一次，落回 HAP 特征
```

### 为什么第 2 步要"乐观更新"

设备从收到指令到上报新状态，中间有 10–60 秒。如果等设备回了才更新界面，
用户会觉得"拖了没反应"。所以先改界面，再用设备真实值校正。

### 为什么第 3 步要防抖

iOS 拖动滑块会连续产生几十次写请求。不防抖的话，设备侧会收到几十条指令，
触发节流后大部分被丢弃，最终值是随机的。

## 数据流：一次读取

```
hap 每 8 秒 → GET /devices/{id}/state → bridge 缓存 → 落到 HAP 特征
```

**为什么是 8 秒**：设备侧 60 秒上报一次，8 秒轮询能保证界面延迟不超过一个上报周期，
又不会给 bridge 造成压力。这个值可以通过 `AIRMX_HAP_POLL_SECONDS` 调。

## 状态接口（可观测性）

`hap` 额外监听 51827，提供只读的 `/status`：

```bash
curl -H "Authorization: Bearer $TOKEN" localhost:51827/status
```

返回每台设备的：

| 字段 | 用途 |
|---|---|
| `online` / `available` | 区分"设备离线"和"配件不可用" |
| `snapshot` | 设备上报的原始语义值 |
| `characteristics` | 当前 HAP 特征值（对比 snapshot 可发现映射问题） |
| `recent_calls` | 最近 12 次入站与出站记录 |
| `pending_threshold` | 目标湿度是否在等待设备确认 |
| `service_names` | 每个服务的实际名字（用于判断 iOS 是否改写） |

**为什么单独做一个接口**：容器日志在 DSM 上打不开，出问题时只能靠猜。
有了它，绝大多数写入类问题三步内可定位。

## 几个刻意的设计取舍

### 1. 状态文件用宿主目录，不用命名卷

```
- ./data:/data
```

命名卷里的文件无法从外面检查。而这个文件（`hap.state`）丢了 = 配对丢了，
必须能一眼看到它是否存在。

### 2. 容器以 root 启动，随后降权

```
user: "0:0"        # compose
_prepare_state_dir()  # 代码里 chown 后 setuid(10001)
```

只为了修正 `/data` 属主。长期以 root 跑没必要。

### 3. 服务顺序一旦定稿就不许动

HAP 的 IID 按服务注册顺序分配，iOS 缓存着 IID → 特征的映射。
**配对之后重排服务 = 全部配件"无响应"**，只能重新配对。

所以 `accessory.py` 里的服务创建顺序有注释保护，`tests/test_guards.py` 里也有断言。

### 4. 不做"按了没反应"的功能

如果一个能力在 HomeKit 里没有对应的控件（比如童锁、水位），
宁可只保留特征不画界面，也不做成一个假开关。
