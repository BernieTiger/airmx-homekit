# 协议字段与机型能力

> 本文只记录**字段语义与实测结论**，不含签名算法实现。
> 指令签名需要你自行抓包比对——这是刻意的取舍：贴出签名实现等于给所有同型号设备开后门。

---

## 字段表

设备状态与指令共用一个扁平字段集合（通过 MQTT 传输）。

| 字段 | 类型 | 读 | 写 | 说明 |
|---|---|---|---|---|
| `power` | 0/1 | ✅ | ✅ | 开关机 |
| `mode` | int | ✅ | ✅ | 模式，见下表 |
| `cadr` | int | ✅ | ⚠️ | 风量。A3S 0–100，A5 1–7 |
| `hThreshold` | int | ✅ | ✅ | 目标湿度（%） |
| `lock` | 0/1 | ✅ | ✅ | 童锁 |
| `anion` | 0/1 | ✅ | ✅ | 负离子（仅 A3S 有硬件） |
| `water` | int | ✅ | ❌ | 水位原始值 **0–120**，不是 0–100 |
| `h0` / `t0` | int | ✅ | ❌ | 机身湿度/温度，**×100 定点数** |
| `h` / `t` | int | ✅ | ❌ | 分体蓝牙计湿度/温度，同样 ×100 |
| `gooseOnline` | 0/1 | ✅ | ❌ | 分体计是否在线 |
| `isNeedClean` | 0/1 | ✅ | ❌ | 是否需要清洁 |
| `cleanNotify` | 0/1 | ✅ | ✅ | 清洁提醒开关（A5 忽略） |
| `pirLock` | 0/1 | ✅ | ✅ | 接近感应（不在状态包里，单独接口） |
| `powerHeat` | 0/1 | ✅ | ✅ | 电辅热（仅 A5） |
| `wifiSignal` | int | ✅ | ❌ | 信号强度 |
| `version` | str | ✅ | ❌ | 固件版本 |

### 两个必须记住的坑

1. **传感器缺失用 `99999` 表示**，不是 0。解析时 `99999` 和 `<=0` 都要当无效
2. **`water` 满量程是 120**，直接当百分比用会算错（25/120 = 20.8%，不是 25%）

## 模式枚举

| 值 | 含义 | HomeKit 呈现 |
|---|---|---|
| 0 | 手动（面板显示 M） | 加湿 |
| 1 | 自动 | 自动 |
| 2 | 睡眠 | 独立开关 |
| 5 | 故障 | 不暴露 |
| 3/4/6 | 未知，网关原样透传 | 不暴露 |

### 面板上的 50 / 45 / 40 不是模式

按机身按钮会依次出现 M / 50 / 45 / 40 / 睡眠，容易误判成五种模式。

**实际上 50/45/40 是「目标湿度预设」**：按一下就把 `hThreshold` 设成 50/45/40，仍在手动档。
所以它们对应 HomeKit 里的「目标湿度」滑块，不需要额外的模式。

### 自动档的两个反直觉行为

1. **iOS 在自动档会隐藏目标湿度滑块**（苹果认为目标由配件决定）。
   想改目标必须先切回「加湿」档
2. **设备进入自动后可能自己改写目标湿度**（实测 A5 从 30 改成 40）

## 机型能力矩阵

| 项目 | A3S（model 20/21） | A5（model 10/11） |
|---|---|---|
| 风量 | 0–100，量化到偶数 | 1–7 档 |
| 负离子 | ✅ | ❌ |
| 电辅热 | ❌ | ✅ |
| 机身温湿度传感器 | ✅ | ❌（h0/t0 = 99999） |
| 分体蓝牙计 | 可选 | 标配 |
| cleanNotify | ✅ 有效 | ❌ 写入无回执 |
| 调风量需先切手动 | 否 | ✅ 是 |
| 水位满量程 | 120 | 120 |

**写代码时的判断依据**：不要按型号 if/else，按能力布尔值。见 `hap/profiles.py`。

## 字段探测方法

这是本文最有价值的部分——拿到一台新机型时怎么摸清它。

### 原则：一次只改一个字段

```bash
# 1. 读当前状态
curl -s -H "Authorization: Bearer $TOKEN" localhost:25888/devices/{id}/state

# 2. 写入单个字段
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"cadr":60}' localhost:25888/devices/{id}/control

# 3. 等 15 秒后读回，确认真被采纳
curl -s -H "Authorization: Bearer $TOKEN" localhost:25888/devices/{id}/state
```

**回执里带的是你下发的指令，不代表设备采纳了。** 必须读回状态确认。

### 判断字段的真实语义

| 现象 | 结论 |
|---|---|
| 写 X 后读回 X | 可写字段 |
| 写 X 后读回旧值 | 只读，或该机型不支持 |
| 写 0 后读回 1 | 是**能力标志**，不是开关（例：`uv`） |
| 写后读回被量化（如 45→44） | 设备有步进，映射层要跟着量化 |
| 写入成功但状态包里没有 | 该字段走独立接口（例：`pirLock` 在 settings） |

### 建立能力矩阵

每测一个字段，记一行：机型 / 字段 / 读 / 写 / 回执 / 备注。
测完 10–15 个字段，能力矩阵就出来了，再决定哪些暴露给 HomeKit。

**不要凭 APK 里的字段列表就认定设备支持**。APK 里有、真机写入恒回 0 的字段很多
（如 `delayOffTimer`、`electrolysis`），照抄会做出按了没反应的假开关。

## 关于指令签名

设备会校验指令的完整性。签名机制需要你自己从抓包中比对得出。

本文不提供实现，原因有两点：

1. 贴出来等于给所有同型号设备开了一个后门
2. 厂商已停服，签名机制不再更新，任何公开的实现都会长期有效

**这不会阻碍复现**——你抓一次自己的设备、改一个字段、对比前后报文，就能定位出签名覆盖的字段范围。
